## 2026-07-07 — cts-sync.sh: self-overwrite of .claude/scripts/cts-sync.sh mid-run produces a spurious syntax-error exit code

Why: `cts-sync.sh` copies `.claude/scripts/` last in the payload order specifically so it overwrites itself only after everything else is synced (see comment above `sync_path()`). But bash does not fully buffer a script's source before executing straight-through code — when `copy_one` overwrites the running script file on disk, bash's subsequent reads for the remainder of the script land on bytes from the _new_ file at the _old_ file's byte offset, which don't align to any coherent statement. Observed result: the run completes all real work (payload copied/merged, `.cts-version` written, "Done. Review with: git diff" printed) but then bash throws a parse error and the process exits non-zero. Verified via `.cts-version` matching the new upstream SHA and `git diff --stat` matching the printed merge/conflict list — the non-zero exit does not mean the sync failed, contradicting the assumption in `.claude/skills/cts-update/SKILL.md` step 2 that non-zero exit means "did not run." Re-verified 2026-07-07 in an isolated sandbox after this exact sync pulled a new `cts-sync.sh` revision (commit `c512bd8`, which only reworked `merge_one`'s temp-file cleanup and left the self-copy ordering/comment untouched): reproduced the same class of failure with a synthetic mid-file upstream diff to `cts-sync.sh` (exit 127, `line: command not found` — a _different_ garbled error than the original run's `exit 2, syntax error near unexpected token '&&'`, confirming the error text/code is arbitrary noise from misaligned byte offsets, not a stable signal) — so the bug is still present in the version currently installed at `.claude/scripts/cts-sync.sh`. Root cause is structural (self-modifying script under `bash script.sh` invocation) and needs a fix in the sync engine itself, e.g. re-exec via `exec bash "$0" "$@"` right before the self-copy, or defer the self-copy to a `trap ... EXIT` that runs after the interpreter has already finished reading the file, or simply copy `.claude/scripts/cts-sync.sh` to a temp path and `cp` it into place as the very last statement with no code after it. Belongs in: .claude/scripts/cts-sync.sh (code fix — approach not yet decided, see three candidates above) — also `.claude/skills/cts-update/SKILL.md` step 2 wording should note this known false-negative on exit code

## 2026-07-15 — [IMPORTANT — contribute to CTS] docs: markdown prose wrapping is now enforced by Prettier (`proseWrap: never`), not a hand-written agent rule

Why: A first attempt fixed hard-wrapped prose in `docs/SKELETON.md` and added `rules/docs-style.md` as a manual convention for agents to follow — but manual/agent reflow missed several list-item continuations (README numbered steps, DECISIONS "alternatives rejected" bullets) that a mechanical tool catches every time. Since `.md` files already run through `prettier --write` on every commit via `lint-staged`, added `"proseWrap": "never"` to `.prettierrc` instead and ran it across all project-owned docs (root docs, `docs/**`, `rules/**`, `libs/**/README.md`; `.claude/**` and vendored `postgres-best-practices` skill excluded from this pass). Discovered and fixed two pre-existing landmines this exposed: Prettier's markdown parser merges any block with no blank line between two logically-distinct lines into one paragraph — this silently destroyed a table in `rules/workflow.md` ("Frontend agent selection" table had no blank line before it) and glued together two bold-label lines in `libs/identity/infrastructure/README.md` (`**Tags**`/`**May import**` with no blank line between them). Both were pre-existing markdown-authoring bugs, not something Prettier introduced — fixed by adding the missing blank line at the source. `rules/docs-style.md` was rewritten to describe Prettier as the enforcement mechanism (plus the blank-line-before-structural-element gotcha) rather than a convention agents must remember. User flagged this as important and worth contributing upstream — logged in `docs/CLAUDE_TS_CHANGELOG.md` as `pending-port` (not yet run through `/cts-contribute`, deliberately deferred to a dedicated session since the inbox has 20 other unplaced entries that would otherwise gate that flow). ## 2026-07-21 — CI: `apps/web/src/environments/environment.ts` is gitignored/generated, and two workflow jobs independently forgot to produce it

Why: `environment.ts` exports `TELEGRAM_BOT_USERNAME` and is git-ignored (generated from `environment.example.ts` locally, or from a Docker `ARG`/`printf` in the image build). The `e2e` job in `.github/workflows/ci.yml` ran `pnpm nx build web` with no step creating the file at all (esbuild resolver + TS2307 failure), while the separate `build-images` job's Dockerfile _did_ generate it but the workflow's `docker/build-push-action` step never passed `build-args: TELEGRAM_BOT_USERNAME=${{ secrets.TELEGRAM_BOT_USERNAME }}`, so the Dockerfile's own `test -n` guard failed closed. Fixed both: added a "Generate Angular environment files" step (copies `environment.example.ts` → `environment.ts`/`environment.development.ts`) before the e2e build, and added the missing `build-args` line to the image-build step. Requires a `TELEGRAM_BOT_USERNAME` GitHub Actions secret to be configured for `build-images` to produce a real (non-empty) value. Belongs in (guess): rules/git-operations.md or a new CI note — any future job that runs `nx build web` or builds the web Docker image needs this same environment-generation step; worth a comment in `ci.yml` itself so it isn't silently dropped again

## 2026-07-21 — Dockerfile build-arg validation logic has zero automated test coverage

Why: Fixed a CWE-88-style injection in `apps/web/Dockerfile` — `TELEGRAM_BOT_USERNAME` was interpolated unescaped via `printf` into a single-quoted JS string literal when generating `apps/web/src/environments/environment.ts`, so a value containing `'` or `\` could break out and inject code into the bundled Angular artifact. Fixed by adding a `grep -E '^[A-Za-z0-9_]+$'` charset-validation `RUN` step before the `printf`, rejecting non-alphanumeric/underscore values with a clear error. Verified manually via `docker compose build --build-arg TELEGRAM_BOT_USERNAME=...` with valid (`test_bot`, passes) and unsafe (`test'bot`, `test\bot`, both correctly fail) values — but `tester` flagged that this validation is shell embedded in the Dockerfile `RUN` chain and is invisible to `nx test web`/`api` (Vitest never builds the image), so a future edit to that Dockerfile stanza could silently reintroduce the injection with no CI signal. Belongs in (guess): a CI step in `.github/workflows/ci.yml`'s `build-images` job (or a dedicated job) that builds the `apps/web` image with a deliberately malicious `TELEGRAM_BOT_USERNAME` build-arg and asserts non-zero exit — not yet implemented, this entry is the pointer
