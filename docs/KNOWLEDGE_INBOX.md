## 2026-07-07 — cts-sync.sh: self-overwrite of .claude/scripts/cts-sync.sh mid-run produces a spurious syntax-error exit code

Why: `cts-sync.sh` copies `.claude/scripts/` last in the payload order specifically so it overwrites itself only after everything else is synced (see comment above `sync_path()`). But bash does not fully buffer a script's source before executing straight-through code — when `copy_one` overwrites the running script file on disk, bash's subsequent reads for the remainder of the script land on bytes from the _new_ file at the _old_ file's byte offset, which don't align to any coherent statement. Observed result: the run completes all real work (payload copied/merged, `.cts-version` written, "Done. Review with: git diff" printed) but then bash throws a parse error and the process exits non-zero. Verified via `.cts-version` matching the new upstream SHA and `git diff --stat` matching the printed merge/conflict list — the non-zero exit does not mean the sync failed, contradicting the assumption in `.claude/skills/cts-update/SKILL.md` step 2 that non-zero exit means "did not run." Re-verified 2026-07-07 in an isolated sandbox after this exact sync pulled a new `cts-sync.sh` revision (commit `c512bd8`, which only reworked `merge_one`'s temp-file cleanup and left the self-copy ordering/comment untouched): reproduced the same class of failure with a synthetic mid-file upstream diff to `cts-sync.sh` (exit 127, `line: command not found` — a _different_ garbled error than the original run's `exit 2, syntax error near unexpected token '&&'`, confirming the error text/code is arbitrary noise from misaligned byte offsets, not a stable signal) — so the bug is still present in the version currently installed at `.claude/scripts/cts-sync.sh`. Root cause is structural (self-modifying script under `bash script.sh` invocation) and needs a fix in the sync engine itself, e.g. re-exec via `exec bash "$0" "$@"` right before the self-copy, or defer the self-copy to a `trap ... EXIT` that runs after the interpreter has already finished reading the file, or simply copy `.claude/scripts/cts-sync.sh` to a temp path and `cp` it into place as the very last statement with no code after it.
Belongs in (guess): claude-ts-upstream (cts-sync.sh script) — also `.claude/skills/cts-update/SKILL.md` step 2 wording should note this known false-negative on exit code

## 2026-07-14 — CI Actions SHA-pinning: `git ls-remote refs/tags/<tag>` can return an annotated-tag object SHA, not the commit SHA

Why: While pinning all `.github/workflows/*` actions to 40-char SHAs, a devops agent resolved `pnpm/action-setup@v4` via `git ls-remote https://github.com/pnpm/action-setup refs/tags/v4` and got `f40ffcd9367d9f12939873eb1018b921a783ffaa` — a real 40-hex-char value, so it looked correct. But `v4` on that repo is an **annotated** tag: `refs/tags/v4` resolves to the tag _object_, and only `refs/tags/v4^{}` (the dereference syntax) resolves to the actual commit it points at (here, `b906affcce14559ad1aafd4ab0e942779e9f58b1` — a different SHA). The other 6 actions pinned in the same pass (`actions/checkout`, `actions/setup-node`, `nrwl/nx-set-shas`, `actions/cache`, `docker/setup-buildx-action`, `docker/build-push-action`) all happened to use lightweight tags, where `refs/tags/<tag>` already equals the commit SHA — so the bug wouldn't have been caught by pattern-matching "is this 40 hex chars," only by independently re-resolving every pin and diffing. General rule: when resolving a tag to a commit SHA for pinning, always query `refs/tags/<tag>^{}` (or use `gh api repos/<owner>/<repo>/commits/<tag>` which returns the commit directly) — never trust the bare `refs/tags/<tag>` SHA without checking whether the tag is annotated.
Belongs in (guess): rules/dependencies.md or a `security-scanner` checklist item ("verify each SHA-pin resolves via `^{}` dereference, not raw tag ref")

## 2026-07-13 — GitHub Actions `services.<name>.options` health-cmd needs single-token quoting, not docker-compose array syntax

Why: While adding a `mongo:7` service container to `.github/workflows/ci.yml`, the first-pass health-check used `--health-cmd mongosh --eval "db.adminCommand('ping')"` — syntactically valid YAML, but GH Actions passes `services.*.options` straight to `docker create`, which parses `--health-cmd` as taking exactly one token; the trailing `--eval "..."` became unrecognized positional args and `docker create` failed with `unknown flag: --eval`, exit 125 (verified locally by reproducing the exact `docker create` call). This means the service container would never be created and the CI job would fail before any step ran — a silent trap because the YAML itself has no lint error. Fix: wrap the whole command as one quoted token, e.g. `--health-cmd "mongosh --eval \"db.adminCommand('ping')\""`. The `docker-compose.yml` array healthcheck form (`test: ['CMD', 'mongosh', '--eval', "..."]`) does not translate directly to GH Actions service `options` syntax. Always dry-run `docker create --health-cmd ... <image>` locally before trusting `services.*.options` health-cmd quoting in CI.
Belongs in (guess): rules/docker-commands.md or rules devops skill (GH Actions service-container health-cmd quoting gotcha)

## 2026-07-14 — local `penny-mongo` container logs continuously with app stopped: it's the compose healthcheck, not a bug

Why: Investigated a report of `penny-mongo` emitting logs nonstop while no app container was running. `docker ps` confirmed only `penny-mongo` (healthy, 18h uptime) was up — no app/worker was crash-looping or hammering it. The recurring ~10s bursts (`Connection accepted` → `client metadata: application.name "mongosh 2.8.3", env.container.runtime: docker` → `Connection not authenticating` → `Received first command` → `Connection ended`) are the `docker-compose.yml` mongo service's own `healthcheck` (`mongosh --eval "db.adminCommand('ping')"`, `interval: 10s`) pinging itself from `127.0.0.1` inside the container — not the app, and `"Connection not authenticating"` is informational (pings run credential-less), not an auth failure. Negligible resource cost (0.32% CPU / 79 MiB). General lesson: don't assume "container is logging but the app isn't running" means something is wrong — check the compose file's `healthcheck` block and match its `interval` against the log cadence before treating it as a bug. To quiet it (optional, not a fix): raise `interval` or add `command: ['--quiet']` to the mongo service.
Belongs in (guess): rules/docker-commands.md (note that compose healthchecks are a normal source of "continuous log" reports)

## 2026-07-13 — `@nx/enforce-module-boundaries` has two independent axes (`scope` and `platform`); fixing one tag can still leave a violation on the other

Why: Backfilling the missing `eslint.config.mjs` for the hand-scaffolded lib above (see prior entry) surfaced a real boundary violation once lint actually ran: `libs/shared/testing` (tagged `scope:shared`, `platform:shared`) imported `IUserRepository` from `identity-core` (`scope:identity`, `platform:server`) — banned because `scope:shared` may only depend on `scope:shared`. The obvious fix (retag to `scope:identity`) is necessary but NOT sufficient: the lib was still tagged `platform:shared`, and `platform:shared` may only depend on `platform:shared` — so `identity-core`'s `platform:server` tag would have re-triggered the same class of error post-retag if only `scope` had been corrected. `ddd-architect` review caught both axes before implementation; the fix was `libs/identity/testing` tagged `["scope:identity", "type:testing", "platform:server"]` (matching the domain lib it's coupled to on both dimensions, not just one). ## 2026-07-13 — identity: CAS-via-optional-param is the established pattern for closing TOCTOU races on Mongo scoped-updates

Why: Two structurally identical stale-read-modify-write races (`SetUserStatusService`/`updateStatus`, `admin-promote.command.ts`/`updateRoles`) were fixed with the same shape: the repository method (`mongo-user-repository.ts`) gains an _optional_ `expectedCurrentValue` param that, when present, adds `{_id, field: expectedValue}` to the `findOneAndUpdate` filter (Mongo array fields use `{field: {$eq: expectedArray}}` for exact match — equivalent to the bare shorthand, `$eq` just self-documents); `findOneAndUpdate` returns `null` on mismatch. Callers capture the pre-write value from their own prior read and pass it through; on `null` they surface an explicit, observable failure (409 `DomainError.conflict()` in the HTTP path, `logger.error` + `process.exit(1)` in the CLI path) — never a silent retry. The optional-param design means old callers (e.g. `dev-token.command.ts`, still using the 2-arg no-CAS shape) get byte-identical behavior, so the pattern rolls out incrementally without a breaking change. This is now the second and third instance of this shape in the codebase (a status-immutability precedent already existed) — worth documenting as the canonical fix for any future TOCTOU finding on a Mongo entity field, rather than re-deriving it each time.
Belongs in (guess): rules/architecture-backend.md (Mongo scoped-update / CAS pattern) or PROJECT_CONTEXT.md

## 2026-07-14 — nx: `@nx/vitest`-based projects need a manually-added `typecheck` target; `@nx/vite/plugin`'s `typecheckTargetName` only auto-generates one for `@nx/vite:build` projects

Why: A confirmed repo-wide gap: `nx.json` registers `@nx/vite/plugin` with `"typecheckTargetName": "typecheck"`, but that option only materializes a `typecheck` target for projects whose test target comes from `@nx/vite:build`. Projects whose test target is inferred by `@nx/vitest` (11 of 16 vitest-covered projects here: apps/api, apps/cli, libs/identity/{application,core,infrastructure}, libs/shared/{contracts,errors,infrastructure,kernel,util,validation}) got no `typecheck` target at all — `nx build` type-checks only lib source (excludes `*.spec.ts` via `tsconfig.lib.json`), and vitest transpiles specs via esbuild with zero type-checking. Net effect: a type error in a spec file (wrong mock shape, stale import, `any`-typed mock hiding a real error) could pass silently forever. `@nx/vitest` has no plugin-level typecheck option and `@nx/js:tsc` is emit-oriented (wrong shape for a noEmit typecheck-only target) — verified via `nx show project <native-typecheck-project> --json` that Nx's own inferred `typecheck` target is itself just `nx:run-commands` running `tsc --noEmit -p <tsconfig>`, so replicating that exact pattern by hand (not a raw shell-out workaround) is the idiomatic fix. Two related gotchas surfaced while fixing it: (1) `nx.json`'s `targetDefaults` keys match by **target name**, not executor — a `targetDefaults.typecheck` block applies uniformly to every target literally named `typecheck` across the workspace, whether manually declared in `project.json` or plugin-inferred, so cache config can be centralized in one place instead of duplicated per-project; (2) the `production` named input explicitly excludes spec files and `tsconfig.spec.json` (`nx.json`'s `namedInputs`) — any target that typechecks against `tsconfig.spec.json` must use `"default"` (which includes spec files) in its cache `inputs`, or the cache will hide changes to the very files being checked.
Belongs in (guess): rules/architecture-backend.md or a dedicated Nx section (typecheck-target-per-plugin gotcha + targetDefaults-by-name-not-executor + production-excludes-specs caching rule) — also relevant to `rules/workflow.md`'s Command Execution Policy table, already updated with the basic invocation but not this deeper mechanism
