## 2026-07-21 — [ci] An unset GitHub Actions `secrets.*` evaluates to empty string with no error, and masking makes the resulting misconfiguration undebuggable — use `vars.*` for non-sensitive config

Why: A `build-images` failure was `${{ secrets.TELEGRAM_BOT_USERNAME }}` resolving to nothing because the secret had not been created yet; the workflow passed an empty `--build-arg` and the Dockerfile's `test -n` guard emitted a generic message pointing at the Dockerfile rather than at the missing secret. GitHub documents both halves of this trap: an unset secret silently becomes an empty string, and secrets cannot be used in `if:` conditionals, so you cannot cheaply assert their presence. Compounding it, secrets are masked as `***` in logs by design — so when the value is merely _wrong_ rather than missing, the logs cannot distinguish the two. GitHub's own criterion is sensitivity, not repo-hygiene: "if you need greater security for sensitive information such as passwords or API keys, you should use secrets instead of variables" (docs.github.com, Variables › Security Considerations). Configuration **variables** (`vars.*`, scopable to repository/organization/environment) are the correct vehicle for non-sensitive per-environment values — they render in plain text, so they are debuggable. Rule of thumb: masking is a cost paid for confidentiality; when the value is not confidential you pay the cost and receive nothing. Belongs in: a CI/secrets-handling rule — no `rules/local/` CI file exists yet; stack-agnostic, so `claude-ts-upstream` too.

## 2026-07-21 — [ci] An `actions/cache` key must encode everything that determines the cached CONTENT, not just the lockfile — an exact key hit skips the save step, so a stale cache persists silently forever

Why: The Playwright browser cache was keyed `playwright-${{ hashFiles('pnpm-lock.yaml') }}`, but its content is determined by the installed browser SET, which the key did not encode. When the install step changed from chromium-only to all three engines, `pnpm-lock.yaml` was untouched, so the key still hit exactly — and `actions/cache` skips its post-job save on an exact hit. The steady state would have been: restore chromium-only cache → download firefox + webkit → save nothing → repeat forever, with tests passing the whole time and nothing in the logs announcing the waste. Confirmed empirically in both directions: the pre-fix run's final step read `skipped Post Cache Playwright browsers`, while the post-fix run (key prefix bumped `playwright-` → `playwright-all-`, `restore-keys` bumped to match so a stale entry cannot be partially restored) read `Cache not found for input keys: playwright-all-…` → downloads → `Cache saved with key: playwright-all-…`. Generalises to any cache whose content depends on a step's arguments rather than only on a manifest — the lockfile pins the tool VERSION, not which artefacts you asked it to fetch. Also recorded for calibration: the full three-engine e2e job ran 1m43s cold, so the "installing all browsers is too slow for CI" premise behind the original chromium-only install did not hold. Belongs in: a CI-caching rule — stack-agnostic, so `claude-ts-upstream` material too.

## 2026-07-21 — [ci] A GitHub Actions run marked "failure" can be mostly green — always read job-level conclusions before concluding the pipeline is broken

Why: One run showed as `failure` in the UI and in pasted logs, and was reasoned about (including by a dispatched `devops` agent working only from those logs) as "the pipeline is still failing." `gh run view <id> --json jobs` showed `ci` ✅, `build-images` ✅, `e2e` ❌ — two of three jobs were already green, and the only remaining defect (missing Playwright firefox/webkit binaries) was unrelated to the work everyone was chasing. Run-level status is the OR of its jobs, so a 2/3-green run and a 0/3-red run are visually identical; pasted log excerpts flatten this further by showing one job at one moment on one branch. Practical consequence: an agent without GitHub API access cannot distinguish these states and will over-report breakage — authenticate `gh` (read scopes suffice: run status, job breakdown, `--log-failed`, and file contents at any ref were all this investigation needed) before diagnosing CI. Belongs in: a CI-diagnosis rule — plus a note that `gh` read access is worth having configured.

## 2026-07-23 — [config] Claude Code Bash allow rules are evaluated per-subcommand — a trailing `*` never authorizes chained commands, and compound patterns should be decomposed

Why: Per the permissions docs (§ Compound commands): "a rule like `Bash(safe-cmd *)` won't give it permission to run `safe-cmd && other-cmd`. The recognized command separators are `&&`, `||`, `;`, `|`, `|&`, `&`, and newlines. A rule must match each subcommand independently." Consequences applied here: (1) 26 accreted per-lib entries of the form `Bash(set -a && source .env && set +a && pnpm nx test <lib>)` were replaced by 4 composable rules — `Bash(set -a)`, `Bash(set +a)`, `Bash(source .env)`, `Bash(pnpm nx test *)` — covering every current and future lib with no settings churn while staying chain-safe; (2) wildcard allows like `Bash(grep *)`/`Bash(jq *)` are safe to commit at project level, while `cat`/`find`/`awk`/`sort` stay local-only (they can read `.env`, `-exec`, `system()`, or `-o`-overwrite — Read deny rules govern the Read tool, not Bash file reads); (3) `Bash(rm -rf *)` deny is prefix-fragile — an `rm -fr` variant was added, but deny rules are a speed bump, not a sandbox. Belongs in: a settings/permissions-authoring rule — `claude-ts-upstream` material, since it describes harness behaviour rather than anything project-specific.

## 2026-08-07 — [lint] `@nx/dependency-checks` can mask `@nx/enforce-module-boundaries` when probing a banned-import rule with a package not yet declared anywhere

Why: to verify a newly added `bannedExternalImports` entry actually fires, a probe planted `import { ObjectId } from 'bson'` in a `type:core` lib. Lint failed non-zero as expected, but the reported error was `@nx/dependency-checks` ("missing from dependencies"), not `@nx/enforce-module-boundaries` — a false positive for the thing under test, since a lib that already declared the package as a dependency would never hit this rule at all. Root cause: `@nx/dependency-checks` validates that every package actually imported by a project is declared in that project's own `package.json`, and runs independently of (and apparently before, in reported output) the module-boundary rule. Fix for probing: temporarily add the package at its already-resolved lockfile version (exact-pinned, e.g. `"bson": "6.10.4"` — check `pnpm-lock.yaml`/a sibling project's `package.json` for the resolved version rather than guessing) to the target project's `package.json`, re-run, confirm the boundary error specifically, then revert. Generalises to any future banned-import probe against a package the workspace doesn't already depend on directly. Belongs in (guess): a new `rules/local/` or `rules/cts/` Nx-lint-probing note — no existing rule file documents this interaction; `nx-generators.md`/`workflow.md`'s Nx command policy are the closest candidates but neither currently covers probing `enforce-module-boundaries` in isolation.

## 2026-08-07 — [lint] `eslint.config.mjs`'s two `depConstraints` blocks (main + `**/*.spec.ts` override) must be checked independently — a flat merge across both hides a real unfenced-tag gap

Why: building a guard spec to catch `scope:*`/`type:*` tags with no matching `sourceTag` entry in `depConstraints`, the first implementation regex-scanned the whole file into one merged `Set<string>` of source tags. This missed a real, live gap: `libs/identity/testing`'s `type:testing` tag had a `sourceTag` entry in the `**/*.spec.ts` override block only, not in the main block — so the merged-set guard read it as "covered" while the main `@nx/enforce-module-boundaries` rule left every non-spec `.ts` file in that lib completely unfenced. Root cause: ESLint flat-config rule keys replace rather than merge across matching config objects, so this repo's two blocks are independent coverage domains by design (confirmed via the file's own comment) — any tag-coverage tooling must extract and check `depConstraints` per block (e.g. via a bounded per-block regex, or dynamic `import()` of the config module and iterating each flat-config array item's own `rules['@nx/enforce-module-boundaries'][1].depConstraints`), never as one flattened union. The fix (`apps/web/src/dep-constraints-tag-coverage.guard.spec.ts`) now does the latter. Belongs in: `rules/local/nx-generators.md` (new-lib setup / depConstraints guidance already lives there) or `rules/local/testing.md` (guard-spec conventions) — concrete file exists for either target.

## 2026-08-07 — [testing] `nx test <project>` result caching can serve a stale pass/fail after a dependency file (not the spec itself) was mutated mid-session

Why: while fire-testing a guard spec that reads `eslint.config.mjs` at runtime, editing that file and re-running `pnpm nx test web -- -t "depConstraints"` (no cache flag) served a cached result from before the edit — the guard's assertion did not reflect the just-mutated file. Nx's test-result cache keys on inputs it tracks for the target, and a runtime `import()`/read of a file outside the spec's own dependency graph as understood by Nx does not necessarily invalidate that cache. Fix: append `--skip-nx-cache` whenever a spec under fire-test reads a file that was just edited in the same session, rather than trusting the next `nx test` run to see the change. Belongs in: `rules/local/testing.md` — concrete file exists.

## 2026-07-28 — [process] `git checkout -- <file>` / `git restore` on an uncommitted-only change silently destroys it, no warning

Why: While independently verifying a Tailwind `@source` glob fix, the `tester` agent used `git checkout -- apps/web/src/styles.css` as a "revert to confirm RED" trick — but since the fix was never committed, this reverted all the way to HEAD (pre-fix), destroying the implementer's diff. Belongs in: a git-operations rule (no `rules/local/git-operations.md` exists yet) or the quality-gate agent conventions; stack-agnostic, so `claude-ts-upstream` material.

## 2026-07-27 — [pattern] In-flight promise cache is a separate field from the TTL cache, not a replacement for it

Why: `GetExchangeRatesService.execute()` (`libs/budget/infrastructure/src/lib/get-exchange-rates.service.ts`) needed dedup for concurrent cache-miss calls hitting a rate-limited upstream (Monobank, ~1 req/5min). The fix adds a third field, `inFlightFetch: Promise<T> | undefined`, orthogonal to `cachedResponse`/`cachedAtMs` — cleared via `.finally()` on settle, independent of the TTL write/expiry cycle. Concurrent callers that miss the TTL check all await the _same_ promise object; each then independently runs its own post-await stale-serve/cold-throw logic, so existing single-caller semantics stay untouched with zero branching changes. This is the reusable shape for any other service wrapping a rate-limited external client behind a TTL cache: the dedup slot and the TTL cache are two independent fields, not one merged state machine. Belongs in: `rules/local/architecture-backend.md` (external-client + TTL-cache pattern) **if a second service needs this same treatment** — otherwise discard as a one-off. Deliberately kept pending that second occurrence rather than promoted on a sample size of one.

## 2026-08-07 — [docs] Prettier corrupts markdown when a bold span sits next to an inline-code glob starting with a double asterisk — write the glob in prose instead

Why: writing a bold span immediately followed by inline code containing a leading globstar (the ESLint/minimatch "match any directory" pattern) gives Prettier two readings of the asterisk run — bold-close versus glob-open. It resolves them wrongly and rewrites the line into genuinely broken output: emphasis markers left dangling, backticks glued to adjacent words with the surrounding spaces eaten, and stray backslash escapes inserted mid-pattern. It is silent, happens on `--write`, and the damage is a formatting change rather than an error, so `--check` passes afterward and CI never notices. Hit live this session in `rules/local/workflow.md` while documenting exactly such a glob. Notably this repo already has a commit whose message includes "fix markdown bold/glob corruption" (`e582626`), so this is at least the second occurrence and nothing yet prevents a third — the earlier fix repaired instances without recording the cause. Mitigations, in order of preference: (1) describe the pattern in prose ("a globstar-prefixed `application/**/*.ts` pattern") so no asterisk run ever touches an emphasis marker; (2) if the literal must appear, put it in a fenced code block rather than inline code; (3) never place inline code starting or ending with an asterisk directly adjacent to bold/italic markers. General rule: any inline code span whose content begins or ends with `*` or `_` needs a non-emphasis character between it and any adjacent emphasis marker. Belongs in: a new `rules/local/docs-style.md` (the consumer-owned mirror does not exist yet; `rules/cts/docs-style.md` is the natural topic home but is `Edit`-denied per this file's own header guidance) — and it is stack-agnostic, so it is also a `/cts-contribute` candidate for the upstream docs-style rule.

## 2026-08-07 — [tooling] A static `mise` install path on `PATH` silently ignores the repo's `mise.toml`, giving VS Code tasks the wrong Node

Why: `pnpm exec nx run api:lint` failed from a VS Code task with `ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite` under Node v20.19.5, while the same command from a normal shell succeeded under v22.23.1 — pnpm 11.9.0 requires Node ≥22.13 and loads `node:sqlite`, a 22.5+ builtin. The repo pins Node correctly in three places (`engines.node`, `.nvmrc`, `mise.toml` → 22.23.1), so the pin was not the problem. Root cause: `mise` was never activated via a shell hook (nothing in `~/.bashrc`), and `PATH` instead carried a **static** `~/.local/share/mise/installs/node/<v>/bin` entry. A static install path is frozen at the version it names and cannot re-resolve per directory, so entering the project does nothing — whichever version was baked in at process-launch time wins. The user's global `~/.config/mise/config.toml` pins `node = "20"`, so the GUI-launched VS Code process inherited Node 20 and every task it spawned used it, regardless of the repo's `mise.toml`. Compounding it: VS Code spawns tasks as `/usr/bin/bash -c` (non-interactive, reads no rc file), so an rc-based `mise activate` hook would **not** fix this either. The fix is shims, which are real binaries that consult the nearest `mise.toml` at exec time independent of shell type: `export PATH="$HOME/.local/share/mise/shims:$PATH"` in `~/.profile`, then log out/in so the GUI session inherits it (`mise exec -- <cmd>` is the per-command workaround). General principle: a green run in an agent/CLI shell is not evidence the same command works in the editor, because the two can resolve entirely different toolchain versions — when a tool-version error appears only in the editor, compare `node -v` across both before suspecting the repo config. Belongs in: `README.md` setup section (Node/mise prerequisites), or a new `rules/local/environment.md` if editor-vs-shell toolchain drift recurs.

## 2026-08-07 — [eslint] `playwright/no-standalone-expect` only recognizes literal `test`/`describe` wrapper names, not aliases like `it`

Why: a blanket `apps/*-e2e/**/*.ts` glob applied `eslint-plugin-playwright`'s rules to a Vitest project (`api-e2e`) alongside the genuine Playwright projects (`web-e2e`, `smoke-e2e`). The rule flagged every `it(...)`-wrapped `expect()` in `api-e2e` as "standalone," because it pattern-matches the wrapper call's literal name and has no concept of Vitest's `it`/`test` aliasing. Fixed by narrowing the glob to only the genuine Playwright project directories rather than trying to teach the rule about aliases. General principle: any ESLint plugin scoped by a wildcard glob across a monorepo's like-named directories (`*-e2e`, `*-api`, etc.) should be checked against every directory the glob actually expands to, not just the ones it was written for — a glob that "looks right" for the common case can silently apply framework-specific rules to a different framework's files in an edge directory. Belongs in: `rules/local/architecture-backend.md` or a new ESLint-conventions note, flagging that `*-e2e` project globs are not guaranteed framework-homogeneous in this repo.
