## 2026-07-21 — [web/config] `TELEGRAM_BOT_USERNAME` traversed five infrastructure hops to reach exactly one consumer; the API never read it at all

Why: A day of failing CI produced five successive fix commits (`53f0570`, `7571396`, `fe9aadf`, `ceb4dfb`, `b6e1a6b`, all reverted by `ca235cf`), each patching a different hop of the same chain: `.env` → `docker-compose.yml` build arg → Dockerfile `ARG` → `printf` interpolation into generated TypeScript → gitignored `apps/web/src/environments/environment.ts` → Angular bundle. A repo-wide search established that `apps/api` reads only `TELEGRAM_BOT_TOKEN` (`apps/api/src/config/api-config.ts:25`) and that no backend or CLI code reads the _username_ anywhere — so `.env`'s `TELEGRAM_BOT_USERNAME` existed solely to feed the web image's build arg. It was frontend config wearing backend clothes. Two compounding mistakes: the value was treated as a GitHub _secret_ despite being rendered into the DOM by the Telegram Login Widget (`login-page.component.ts:66` sets `data-telegram-login`), and the file it produced was gitignored, so every execution context (ci job, e2e job, Dockerfile, fresh clone) had to independently regenerate it before any `nx` target touching `web` could compile — there was no single place to be correct. The fix direction is deletion, not repair: commit `environment.ts` and remove the whole chain. Worth preserving separately: the Angular side is already well-factored — `TELEGRAM_BOT_USERNAME` is an `InjectionToken` provided once in `apps/web/src/app/app.config.ts:18`, so migrating later to a runtime `/api/config` endpoint (one image for all environments) is a one-line change at the provider, not a refactor. Belongs in (guess): PROJECT_CONTEXT.md (the config-ownership fact + the deferred runtime-config option); the generic lesson about gitignored generated files belongs in a rule

## 2026-07-21 — [ci] An unset GitHub Actions `secrets.*` evaluates to empty string with no error, and masking makes the resulting misconfiguration undebuggable — use `vars.*` for non-sensitive config

Why: The original 2026-07-18 `build-images` failure was `${{ secrets.TELEGRAM_BOT_USERNAME }}` resolving to nothing because the secret had not been created yet; the workflow passed an empty `--build-arg` and the Dockerfile's `test -n` guard emitted a generic message that pointed at the Dockerfile rather than at the missing secret. GitHub documents both halves of this trap: an unset secret silently becomes an empty string, and secrets cannot be used in `if:` conditionals, so you cannot cheaply assert their presence. Compounding it, secrets are masked as `***` in logs by design — which means when the value is merely _wrong_ rather than missing, the logs cannot distinguish the two. GitHub's own criterion is sensitivity, not repo-hygiene: "if you need greater security for sensitive information such as passwords or API keys, you should use secrets instead of variables" (docs.github.com, Variables › Security Considerations). Configuration **variables** (`vars.*`, scopable to repository/organization/environment) are the correct vehicle for non-sensitive per-environment values — they render in plain text, so they are debuggable. Rule of thumb established here: masking is a cost paid for confidentiality; when the value is not confidential you pay the cost and receive nothing. Belongs in (guess): rules/ (a CI/secrets-handling rule) — likely `claude-ts-upstream` too, since it is stack-agnostic

## 2026-07-21 — [nx] `nx affected` has no `-p`/`--projects` flag and silently forwards unrecognised flags to the underlying task command

Why: `pnpm nx affected -p web-e2e -t e2e` did not error at the nx level — nx passed `-p web-e2e` through to the task, producing `playwright test -p web-e2e` → `error: unknown option '-p'`, an error message that points at Playwright and gives no hint that the mistake was in the nx invocation. `--projects` exists on `nx run-many`, not on `nx affected`, and the two are easy to conflate. The replacement used at the time (`nx affected -t e2e --exclude=smoke-e2e,api-e2e`) works but is a denylist and will silently fail to exclude the fourth e2e project someone adds later; a positively-stated scoping mechanism (tags, a distinct target name, or simply `nx run web-e2e:e2e` when the job only ever runs one project) is preferable. Belongs in (guess): rules/workflow.md § Command Execution Policy (Nx Targets)

## 2026-07-21 — [ci] A GitHub Actions run marked "failure" can be mostly green — always read job-level conclusions before concluding the pipeline is broken

Why: The run for `b6e1a6b` showed as `failure` in the UI and in pasted logs, and was reasoned about (including by a dispatched `devops` agent working only from those logs) as "the pipeline is still failing." `gh run view <id> --json jobs` showed `ci` ✅, `build-images` ✅, `e2e` ❌ — two of three jobs were already green and the only remaining defect (missing Playwright firefox/webkit binaries) was unrelated to the environment-file work everyone was chasing. Run-level status is the OR of its jobs, so a 2/3-green run and a 0/3-red run are visually identical; pasted log excerpts flatten this further by showing one job at one moment on one branch. Practical consequence: an agent without GitHub API access cannot distinguish these states and will over-report breakage — authenticate `gh` (read scopes suffice: run status, job breakdown, `--log-failed`, and file contents at any ref were all that this investigation needed) before diagnosing CI. Belongs in (guess): rules/ (a CI-diagnosis rule) — plus a note that `gh` read access is worth having configured

## 2026-07-21 — [tooling] `.mcp.json` `${VAR}` placeholders fail open: an unset variable is passed through literally and surfaces as a vendor auth error, not a config error

Why: The project's committed `.mcp.json` declares `context7` as `npx -y @upstash/context7-mcp --api-key ${CONTEXT7_API_KEY}` (correctly avoiding a literal credential in a tracked file), but `CONTEXT7_API_KEY` was set nowhere — not in the environment, not in shell profiles, not in `.env`. Claude Code started the server anyway with the placeholder unexpanded, so every call returned Context7's _"Invalid API key. API keys should start with 'ctx7sk'"_ rather than anything indicating a missing variable. `claude mcp list` is the diagnostic — its footer reports both `Missing environment variables:` per server and `[Conflicting scopes]` collisions. ## 2026-07-22 — [api/auth] `CsrfGuard` already safe-lists GET/HEAD/OPTIONS globally — no guard/decorator needed for a new unauthenticated GET endpoint

Why: Implementing `GET /api/config` (the runtime bot-config endpoint predicted in the 2026-07-21 `[web/config]` entry below) required deciding how to exempt a new route from auth. Investigation of `apps/api/src/auth/csrf.guard.ts:11,29-31` showed `CsrfGuard` — the only global `APP_GUARD` registered in `AppModule` — already unconditionally safe-lists GET/HEAD/OPTIONS before any session/CSRF check runs, and `SessionGuard`/`ActiveUserGuard` are opt-in per-route via `@UseGuards(...)`, never global. So any new unauthenticated GET handler needs zero guard changes or bypass decorators — simply omitting `@UseGuards` is the entire exemption, exactly as `HealthController`/`HelloController` already do. Confirmed independently by both `reviewer` and `security-scanner` during this task's quality gate as "not a novel/risky pattern." Belongs in (guess): `rules/architecture-backend.md` — saves the next unauthenticated-endpoint task from re-deriving this from scratch.

## 2026-07-22 — [testing] Angular `provideAppInitializer` is unit-testable via `TestBed.inject(ApplicationInitStatus).donePromise` + `provideHttpClientTesting`

Why: The runtime bot-config task replaced a synchronous `useValue` DI provider with `provideAppInitializer` (Angular 17+, successor to the deprecated `APP_INITIALIZER` multi-provider). Testing async bootstrap-time work has no obvious seam — the initializer callback isn't separately exported. The working pattern: configure `TestBed` with `provideHttpClientTesting()`, flush the expected `HttpTestingController` request, then `await TestBed.inject(ApplicationInitStatus).donePromise` (or `await expect(donePromise).rejects...` for failure-path assertions) to observe DI state after the initializer settles — no need to extract the callback into a standalone function for testability. Belongs in (guess): a Angular-testing rule or the `vitest-testing`/`angular-expert` skill.

## 2026-07-21 — [ci] An `actions/cache` key must encode everything that determines the cached CONTENT, not just the lockfile — an exact key hit skips the save step, so a stale cache persists silently forever

Why: The Playwright browser cache was keyed `playwright-${{ hashFiles('pnpm-lock.yaml') }}`, but its content is determined by the installed browser SET, which the key did not encode. When the install step changed from `playwright install --with-deps chromium` to all three engines, `pnpm-lock.yaml` was untouched, so the key still hit exactly — and `actions/cache` skips its post-job save on an exact hit. The steady state would have been: restore chromium-only cache → download firefox + webkit → save nothing → repeat forever, with tests passing the whole time and nothing in the logs announcing the waste. Confirmed empirically in both directions: the pre-fix run's final step read `skipped Post Cache Playwright browsers`, while the post-fix run (key prefix bumped `playwright-` → `playwright-all-`, `restore-keys` bumped to match so a stale entry cannot be partially restored) read `Cache not found for input keys: playwright-all-…` → downloads → `Cache saved with key: playwright-all-…`. Generalises beyond Playwright to any cache whose content depends on a step's arguments rather than only on a manifest — the lockfile pins the tool VERSION, not which artefacts you asked it to fetch. Also recorded for calibration: the full three-engine e2e job runs 1m43s cold (18 tests, 21.4s of actual testing), so the "install all browsers is too slow for CI" premise that motivated the original chromium-only install did not hold. Belongs in (guess): rules/ (a CI-caching rule) — stack-agnostic, so `claude-ts-upstream` material too
