## 2026-08-08 — [process] The sandbox's Bash deny rule blocks `rm -rf` even for legitimate whole-directory deletion (e.g. removing a dissolved Nx lib) — use `find <dir> -type f -delete && find <dir> -depth -type d -delete` instead

Why: an implementation agent deleting the now-empty `libs/budget/validation` lib directory (after colocating all its exports elsewhere, per task) hit a sandbox denial on `rm -rf libs/budget/validation` — the deny rule fires regardless of whether the deletion is destructive-in-the-bad-sense or a legitimate, task-authorized cleanup of a lib with zero remaining consumers. The working substitute confirmed in that session: `find <dir> -type f -delete` (removes all files first) followed by `find <dir> -depth -type d -delete` (removes now-empty directories bottom-up, `-depth` ensures children are removed before parents). Generalises to any future whole-lib-deletion task in this sandbox. Belongs in (guess): `rules/local/shell-scripting.md` if one exists, or a note in `rules/cts/shell-scripting.md`'s sandbox-gotchas section — ambiguous because this may be specific to this project's sandbox config rather than a universal CTS constraint.

## 2026-08-08 — [devops] `nginx.conf`'s `sub_filter` silently no-ops on zero matches — exact-string substitutions (e.g. CSP nonce injection into built `index.html`) need an explicit smoke check, not just a green build

This already happened once and was only caught by manual browser inspection. **Update 2026-08-09: the first remedy — `scripts/web-csp-smoke-check.sh` grepping the served `index.html` for both nonce patterns — was itself insufficient and passed green through a completely unstyled production app.** Verifying that a substitution _landed_ is not the same as verifying the page _works_; see the 2026-08-09 `[testing]` entry on mechanism-vs-outcome assertions. ## 2026-08-08 — [shell] Two `sed`-in-Dockerfile pitfalls that each silently produce a wrong-but-plausible result, caught only by independently recomputing the expected value

> **Note 2026-08-09: the originating code no longer exists.** The build-time hash-injection step was removed from `apps/web/Dockerfile` when `inlineCritical` was disabled — there is no longer an inline `<style>` block to hash, so the CSP carries no `style-src` hash at all. Do not go looking for the `sed` lines described below. **The two `sed` pitfalls themselves remain fully valid and stack-agnostic**, which is why this entry is kept rather than deleted; it is still `rules/cts/shell-scripting.md` / upstream material.

Why: a build-time CSP hash-injection step (computing a sha256 hash of an inline `<style>` block and writing it into an nginx config) shipped two sequential bugs, each passing its own build's `grep -q` verification step while producing the wrong hash. (1) The replacement `sed -i "s|$OLD_HASH|$NEW_HASH|g"` used a hardcoded literal of the _pre-fix_ hash as the search pattern — correct for exactly one commit, then a permanent silent no-op forever after, because GNU sed exits 0 on a zero-match substitution (not caught by `set -e`/errexit). Fix: never match a one-time historical literal; anchor the regex on structure instead (e.g. `s#(directive-name[^;]*)'sha256-[A-Za-z0-9+/=]+'#\1'sha256-$NEW_HASH'#`), or replace a stable placeholder token that never changes. (2) The tag-strip `sed 's/<\/?style>//g'` (no `-E`/`-r` flag) treated `?` as a literal character rather than a quantifier — pure POSIX BRE, not GNU's `\?` extension, and the pattern as written doesn't even invoke that extension correctly — so the tags were never stripped and the hash was computed over `<style>...content...</style>` including markup. Fix: use anchored non-quantifier patterns (`sed -e 's/^<style>//' -e 's/<\/style>$//'`) instead of relying on BRE/ERE quantifier behavior. Both bugs are invisible to a build-succeeded check and to a `grep -q "sha256-$HASH" file` self-verification, because that only confirms _a_ hash landed in the file, not that it's the _hash of the actual served content_ — only an independent, from-scratch recomputation (ideally via a second toolchain, e.g. cross-checking a shell pipeline against Node's `crypto.createHash`) catches this class of bug. Generalises beyond CSP: any build step that computes-then-injects a derived value and self-verifies only "did my write land" rather than "is the written value correct" has this blind spot. Belongs in (guess): `rules/cts/shell-scripting.md`'s sed-gotchas section (stack-agnostic, so also `claude-ts-upstream` material) — ambiguous only in whether it warrants its own subsection or a sentence appended to the existing sed-pitfalls list.

## 2026-07-27 — [pattern] In-flight promise cache is a separate field from the TTL cache, not a replacement for it

Why: `GetExchangeRatesService.execute()` (`libs/budget/infrastructure/src/lib/get-exchange-rates.service.ts`) needed dedup for concurrent cache-miss calls hitting a rate-limited upstream (Monobank, ~1 req/5min). The fix adds a third field, `inFlightFetch: Promise<T> | undefined`, orthogonal to `cachedResponse`/`cachedAtMs` — cleared via `.finally()` on settle, independent of the TTL write/expiry cycle. Concurrent callers that miss the TTL check all await the _same_ promise object; each then independently runs its own post-await stale-serve/cold-throw logic, so existing single-caller semantics stay untouched with zero branching changes. This is the reusable shape for any other service wrapping a rate-limited external client behind a TTL cache: the dedup slot and the TTL cache are two independent fields, not one merged state machine. Belongs in: `rules/local/architecture-backend.md` (external-client + TTL-cache pattern) **if a second service needs this same treatment** — otherwise discard as a one-off. Deliberately kept pending that second occurrence rather than promoted on a sample size of one.

## 2026-08-07 — [tooling] A static `mise` install path on `PATH` silently ignores the repo's `mise.toml`, giving VS Code tasks the wrong Node

Why: `pnpm exec nx run api:lint` failed from a VS Code task with `ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite` under Node v20.19.5, while the same command from a normal shell succeeded under v22.23.1 — pnpm 11.9.0 requires Node ≥22.13 and loads `node:sqlite`, a 22.5+ builtin. The repo pins Node correctly in three places (`engines.node`, `.nvmrc`, `mise.toml` → 22.23.1), so the pin was not the problem. Root cause: `mise` was never activated via a shell hook (nothing in `~/.bashrc`), and `PATH` instead carried a **static** `~/.local/share/mise/installs/node/<v>/bin` entry. A static install path is frozen at the version it names and cannot re-resolve per directory, so entering the project does nothing — whichever version was baked in at process-launch time wins. The user's global `~/.config/mise/config.toml` pins `node = "20"`, so the GUI-launched VS Code process inherited Node 20 and every task it spawned used it, regardless of the repo's `mise.toml`. Compounding it: VS Code spawns tasks as `/usr/bin/bash -c` (non-interactive, reads no rc file), so an rc-based `mise activate` hook would **not** fix this either. The fix is shims, which are real binaries that consult the nearest `mise.toml` at exec time independent of shell type: `export PATH="$HOME/.local/share/mise/shims:$PATH"` in `~/.profile`, then log out/in so the GUI session inherits it (`mise exec -- <cmd>` is the per-command workaround). General principle: a green run in an agent/CLI shell is not evidence the same command works in the editor, because the two can resolve entirely different toolchain versions — when a tool-version error appears only in the editor, compare `node -v` across both before suspecting the repo config. Belongs in: `README.md` setup section (Node/mise prerequisites), or a new `rules/local/environment.md` if editor-vs-shell toolchain drift recurs.

## 2026-08-07 — [eslint] `playwright/no-standalone-expect` only recognizes literal `test`/`describe` wrapper names, not aliases like `it`

Why: a blanket `apps/*-e2e/**/*.ts` glob applied `eslint-plugin-playwright`'s rules to a Vitest project (`api-e2e`) alongside the genuine Playwright projects (`web-e2e`, `smoke-e2e`). ## 2026-08-09 — [devops] Dependabot's default `versioning-strategy` does not guarantee it preserves an exact-pin (`no ^/~`) style — set it explicitly

Why: this repo's non-negotiable exact-pin policy (`rules/cts/dependencies.md`) applies to every version string in `package.json`, including ones Dependabot itself writes. Dependabot's default behavior (`versioning-strategy: auto`, which behaves as "widen unless the manifest looks pinned") is documented to _usually_ preserve exact pins already present, but it is a heuristic, not a hard guarantee tied to this repo's specific policy — it doesn't know the policy exists, it's inferring style from what it sees. ## 2026-08-09 — [testing] Chromium does not surface `X-Frame-Options` frame-blocking via `page.on('console')`, and `contentDocument`/frame-load-timing signals cannot distinguish "blocked by X-Frame-Options" from "loaded but same-origin-policy-restricted" — outcome-level browser testing of this header is not achievable the way CSP-violation testing is

## 2026-08-09 — [devops] `libs/**`/`apps/api`/`apps/cli` `package.json` files are Nx metadata manifests, not real pnpm workspace importers — `@nx/dependency-checks` failures on them are not a "stale lockfile importer" problem

## 2026-08-10 — [devops] A pnpm `overrides` key selects _which_ edges are rewritten; the value is an unconstrained spec and is NOT bounded by the key — always add an upper bound

Why: remediating transitive advisories, an override block was written as `'js-yaml@4': '>=4.3.1'` and `'undici@7': '>=7.29.0'`, on the reasonable-looking assumption that the `pkg@major` selector confines the result to that major. It does not. The key restricts which dependency edges get rewritten; the value is resolved independently, so `>=4.3.1` resolved to `js-yaml@5.2.3` and `>=7.29.0` to `undici@8.10.0` — silently upgrading every consumer across a major boundary. This is strictly worse than the advisory being fixed: a known vulnerability in a tested version was swapped for an untested new major. The tell was that the _original_ vulnerable copies survived alongside the new ones in `node_modules/.pnpm` — a working override replaces a version, it never adds a third. Correct form is a bounded range per major (`'js-yaml@4': '>=4.3.1 <5'`), and after any override change the resolution must be verified against `pnpm-lock.yaml` (authoritative) rather than `node_modules/.pnpm` (which retains stale unpruned directories that look like live resolutions). Belongs in: `rules/cts/dependencies.md`, as a mandatory rule for writing any `overrides` entry.

## 2026-08-10 — [ci] A Dependabot `target-branch` pointing at a fast-forward-only release branch makes every one of its PRs structurally unmergeable

Why: 138 open alerts had accumulated while 15 consecutive Dependabot PRs were opened and closed unmerged. ## 2026-08-10 — [ci] Dependabot groups default to `applies-to: version-updates`, so a group named for a lockstep-sensitive family does not govern that family's security PRs
