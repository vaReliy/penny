## 2026-07-19 — derived-balance `$sum` forces numeric BSON Money storage (not the transport string)

Why: The shared `Money` VO (`libs/shared/util/src/lib/money.ts`) holds `bigint` minor units but `toJSON()` serializes `amount` as a _string_ (`SerializedMoney`, precision-safe for transport). The budget domain's chosen derived-balance strategy aggregates account balance via a Mongo `$sum` over stored transaction amounts — and `$sum` cannot sum strings. Therefore infrastructure must store money as a _numeric_ BSON type (64-bit Long minor units, not int32 which overflows past ~21M UAH, not the transport string), with the mapper round-tripping `bigint ↔ Long` and never touching float. This couples the balance strategy and the money-storage representation. Belongs in (guess): captured permanently by `DECISIONS.md` ADR-007 — delete once the transaction repo/aggregation work records the Long-minor-units storage contract in code.

## 2026-07-27 — averaging two floats then `.toString()` reintroduces the float-precision loss a "decimal string" field was designed to avoid

Why: `reviewer` caught this in the Monobank FX client (`libs/budget/infrastructure/src/lib/monobank-currency-client.ts`, `resolveRateToBase`): `((entry.rateBuy + entry.rateSell) / 2).toString()` can emit `"27.200000000000003"` for real inputs like `27.1`/`27.3`, even though the DTO field (`ExchangeRateEntry.rateToBase`) is explicitly typed and documented as a decimal string specifically to avoid float precision loss in transport. The test fixture used round numbers (41.5/42.1 → exact 41.8) so the bug shipped past the first test pass undetected. Fix pattern: any derived (not passthrough) decimal value bound for a documented precision-preserving string field must be explicitly rounded (`.toFixed(n)`) before serialization — raw float arithmetic output is never safe to hand to `.toString()`. Test fixtures for such code should include at least one operand pair known to trigger binary-float rounding (e.g. `27.1 + 27.3`, `0.1 + 0.2`), not just round numbers that mask the defect. Belongs in (guess): `rules/cts/code-style.md` or `rules/local/code-style-backend.md` — general rule, not budget-specific (same class of bug as float-based Money arithmetic, which `libs/shared/util/src/lib/money.ts` already avoids via bigint).

## 2026-07-22 — Mongoose `autoIndex` builds indexes asynchronously; nothing awaits it by default

Why: Implementing `libs/budget/infrastructure`'s `MongoCategoryRepository` found `getModelForClass(..., { existingConnection })` + `createMongoConnection`'s `await connection.asPromise()` proves socket readiness only, not index-build completion — Mongoose's default `autoIndex: true` builds indexes as a fire-and-forget background op. ## 2026-07-22 — MongoDB `partialFilterExpression` rejects `$exists: false` at index-build time, and Typegoose swallows the failure silently

Why: Same task as above — the Category soft-archive partial unique index was first written as `partialFilterExpression: { archivedAt: { $exists: false } }`, which MongoDB rejects (`Expression not supported in partial index: $not`) — `$exists` is only valid as `true` in this position. Because Typegoose/Mongoose builds indexes in the background (see the entry above), this index-creation failure was never surfaced to the caller: the app booted fine, duplicate-insert tests silently passed because the unique constraint had simply never been created. Fix: use equality-to-null instead — `partialFilterExpression: { archivedAt: null }` — which MongoDB documents as matching "field is null or absent" and is fully supported. Note query filters elsewhere in the same repo correctly use `{ archivedAt: { $exists: false } }` (a _query_, not an index definition) — the two are not interchangeable syntax, only coincidentally equivalent here because the app never explicitly sets `archivedAt: null`. Belongs in (guess): `rules/local/architecture-backend.md` — flag this as the standard soft-delete/archive partial-unique-index recipe so it isn't rediscovered per feature.

## 2026-07-20 — Angular/Playwright test-writing gotchas found during web-shell restyle

Why: Four independent, non-obvious gotchas surfaced while writing/auditing tests for the new `libs/shared/web-shell` shell component and its e2e coverage:

1. `[routerLink]` does not persist as a DOM attribute at runtime — `querySelectorAll('a[routerLink]')` always returns 0 matches; use a structural/positional selector (`nav > a`, or a container-scoped plain `a`) instead when asserting on router-link elements in component specs.
2. `RouterTestingHarness.navigateByUrl(url, ComponentType)` returns the _component instance_, not a `ComponentFixture` — `whenStable()`/`detectChanges()` live on `harness.fixture`, not on the returned value; easy to typo into `TypeError: fixture.whenStable is not a function`.
3. Playwright's `devices['...']` presets set `defaultBrowserType` and cannot be applied via `test.use()` inside a `describe` block ("forces a new worker" error) — only at top-level test-file scope or in the config's `projects` array. For a mobile-viewport-only smoke test layered onto existing chromium/firefox/webkit projects, use `test.use({ viewport: {...}, hasTouch: true })` instead of a device preset.
4. An e2e logout-flow test that mocks `/auth/me` unconditionally will deadlock: `loginGuard` on `/login` re-checks `/auth/me` and bounces an apparently-still-active user straight back, so `page.waitForURL('**/login')` times out. The mock must flip to 401 once the logout endpoint is actually hit, simulating real session invalidation. Belongs in (guess): `vitest-testing`/`playwright-expert` skill notes, or a shared "Angular+Playwright gotchas" reference — none of these are project-specific, they'd help any Angular 17+/Nx/Playwright repo.

## 2026-07-20 — Node's `--env-file` flag does not expand shell-style variable references in .env values

Why: The CLI commands in README.md's "Local dev auth" section failed with `Error: Missing env var: MONGO_URI` even when `.env` was present, because users ran `node --env-file=.env ... ` directly. Node 22's native `--env-file` flag does not perform shell-style variable expansion (e.g., `${MONGO_USER}`) — it reads and sets the literal unexpanded string as the env var value. Since `.env.example` documents `MONGO_URI=mongodb://${MONGO_USER}:${MONGO_PASSWORD}@...` (using bash-style interpolation), the value must be expanded by bash before Node receives it. The fix: source `.env` through bash first with `set -a && source .env && set +a &&` prefixed to the command, which expands all `${...}` references and exports them before Node runs. This is a gotcha any Node.js dev hitting `--env-file` with a `.env` that contains variable references will encounter. Belongs in: README.md's "Local dev auth" section (already fixed via this session) and potentially a shared Node.js troubleshooting reference if the codebase accumulates one.

Why: The legacy bill screen did `bill.value * rate` in floats; the replacement `convertBalanceToCurrency` in `budget-ui` computes `foreignMinorUnits = round(baseMinorUnits × 10^k / rateNumerator)` entirely in `bigint`, splitting the decimal-string rate into `{numerator, denominator}` by string manipulation so `Number`/`parseFloat` never touches it, with round-half-away-from-zero. ## 2026-07-27 — [testing] use `httpController.match(url)`, not `expectOne(url)`, to test concurrent same-URL requests in Angular

Why: `RatesClient.get()` takes no request-differentiating parameter, so two concurrent in-flight calls hit the identical URL and `HttpTestingController.expectOne(url)` throws "matches more than one request" — making race/ordering behavior untestable through the usual API. `match(url)` returns both `TestRequest`s, which can then be `flush()`ed individually in a deliberately chosen order to assert last-write-wins vs. first-write-wins. Used in `rates.store.spec.ts` to document (not fix) the absence of an in-flight guard in `BudgetRequestState.run()`: a `refresh()` issued during a pending `load()` fires a second independent request and whichever resolves last wins, regardless of call order. This is a client-side store race in `BudgetRequestState.run()`, a different concern from server-side `GetExchangeRatesService` request coalescing — no cross-reference to that task. Belongs in (guess): `rules/cts/testing.md` § Angular HTTP testing (CTS-managed — route through `/cts-contribute`), or `rules/local/code-style-angular.md` if kept project-local.

## 2026-07-27 — [frontend] a binary `loading|error|ready` page `state()` computed cannot express post-`ready` partial failure — decide the per-action error convention before screens 17–19

Why: `account-page`'s `state()` computed checks `balance() !== null && rates() !== null` before consulting `error()`, so once the page has succeeded once it can never re-enter `'error'` — a failed `refresh()` set `RatesStore.error()` while the template rendered stale rates with no indication of failure (caught as a `## Fix Now` in task 16's gate). The fix reads `ratesStore.error()` directly in the `ready` branch and renders an inline `role="alert"` beside the still-visible stale data, bypassing `state()` entirely; `BudgetRequestState.run()` already clears `errorSignal` on each call, so recovery clears the banner automatically. This works for a screen with exactly one failable post-load action, but screens 17–19 (records forms, history filter/chart, planner monthly budgets) each have several, and copying the computed as-is means each new failable action needs its own ad hoc bypass. General principle: an all-or-nothing page-level state machine models _initial load_ only — partial/refresh failure is a per-action concern and needs a deliberate convention (per-action error signal surfaced next to its own affordance, stale data never discarded) rather than three more reinventions. Belongs in (guess): `rules/local/code-style-angular.md` as the store/page error-surfacing convention, and worth raising explicitly in the `ba` pass for `2026-07-16-17-screen-records-forms.md` before that screen sets its own precedent.

## 2026-07-27 — [testing] Nx atomized Playwright targets are named `e2e-ci--src/<file>.spec.ts` — discover them, never guess

Why: Running a single e2e spec through Nx requires the exact atomized target string `e2e-ci--src/<filename>.spec.ts`, discoverable via `nx show project <e2e-app> --json` under `metadata.targetGroups`. Guessing the target name produces a "target not found" error, and — worse — `nx affected -t <name>` silently skips projects lacking the named target with no error or warning, so a wrong guess in CI reads as a pass. Related repo-specific gotcha confirmed while writing 360 px viewport assertions: `playwright/no-conditional-in-test` and `no-non-null-assertion` both fire on the natural `boundingBox()` null-check idiom; use `evaluate()` with `getBoundingClientRect()` instead once visibility has already been asserted, which sidesteps both rules.
