## 2026-07-28 — [pattern] In-flight promise cache is a separate field from the TTL cache, not a replacement for it

Why: `GetExchangeRatesService.execute()` (`libs/budget/infrastructure/src/lib/get-exchange-rates.service.ts`) needed dedup for concurrent cache-miss calls hitting a rate-limited upstream (Monobank, ~1 req/5min). The fix adds a third field, `inFlightFetch: Promise<T> | undefined`, orthogonal to `cachedResponse`/`cachedAtMs` — cleared via `.finally()` on settle, independent of the TTL write/expiry cycle. Concurrent callers that miss the TTL check all await the _same_ promise object; each then independently runs its own post-await stale-serve/cold-throw logic, so existing single-caller semantics stay untouched with zero branching changes. This is the reusable shape for any other service in the repo wrapping a rate-limited external client behind a TTL cache (dedup slot + TTL cache are two independent fields, not one merged state machine). Belongs in (guess): `rules/local/architecture-backend.md` (external-client + TTL-cache pattern) if a second service needs this same treatment; otherwise discard as a one-off.

## 2026-07-27 — averaging two floats then `.toString()` reintroduces the float-precision loss a "decimal string" field was designed to avoid

Why: `reviewer` caught this in the Monobank FX client (`libs/budget/infrastructure/src/lib/monobank-currency-client.ts`, `resolveRateToBase`): `((entry.rateBuy + entry.rateSell) / 2).toString()` can emit `"27.200000000000003"` for real inputs like `27.1`/`27.3`, even though the DTO field (`ExchangeRateEntry.rateToBase`) is explicitly typed and documented as a decimal string specifically to avoid float precision loss in transport. The test fixture used round numbers (41.5/42.1 → exact 41.8) so the bug shipped past the first test pass undetected. Fix pattern: any derived (not passthrough) decimal value bound for a documented precision-preserving string field must be explicitly rounded (`.toFixed(n)`) before serialization — raw float arithmetic output is never safe to hand to `.toString()`. Test fixtures for such code should include at least one operand pair known to trigger binary-float rounding (e.g. `27.1 + 27.3`, `0.1 + 0.2`), not just round numbers that mask the defect. Belongs in (guess): `rules/cts/code-style.md` or `rules/local/code-style-backend.md` — general rule, not budget-specific (same class of bug as float-based Money arithmetic, which `libs/shared/util/src/lib/money.ts` already avoids via bigint).

## 2026-07-22 — Mongoose `autoIndex` builds indexes asynchronously; nothing awaits it by default

## 2026-07-22 — MongoDB `partialFilterExpression` rejects `$exists: false` at index-build time, and Typegoose swallows the failure silently

Why: Same task as above — the Category soft-archive partial unique index was first written as `partialFilterExpression: { archivedAt: { $exists: false } }`, which MongoDB rejects (`Expression not supported in partial index: $not`) — `$exists` is only valid as `true` in this position. Because Typegoose/Mongoose builds indexes in the background (see the entry above), this index-creation failure was never surfaced to the caller: the app booted fine, duplicate-insert tests silently passed because the unique constraint had simply never been created. Fix: use equality-to-null instead — `partialFilterExpression: { archivedAt: null }` — which MongoDB documents as matching "field is null or absent" and is fully supported. Note query filters elsewhere in the same repo correctly use `{ archivedAt: { $exists: false } }` (a _query_, not an index definition) — the two are not interchangeable syntax, only coincidentally equivalent here because the app never explicitly sets `archivedAt: null`. Belongs in (guess): `rules/local/architecture-backend.md` — flag this as the standard soft-delete/archive partial-unique-index recipe so it isn't rediscovered per feature.

## 2026-07-20 — Node's `--env-file` flag does not expand shell-style variable references in .env values

Why: The CLI commands in README.md's "Local dev auth" section failed with `Error: Missing env var: MONGO_URI` even when `.env` was present, because users ran `node --env-file=.env ... ` directly. Node 22's native `--env-file` flag does not perform shell-style variable expansion (e.g., `${MONGO_USER}`) — it reads and sets the literal unexpanded string as the env var value. Since `.env.example` documents `MONGO_URI=mongodb://${MONGO_USER}:${MONGO_PASSWORD}@...` (using bash-style interpolation), the value must be expanded by bash before Node receives it. The fix: source `.env` through bash first with `set -a && source .env && set +a &&` prefixed to the command, which expands all `${...}` references and exports them before Node runs. This is a gotcha any Node.js dev hitting `--env-file` with a `.env` that contains variable references will encounter. Belongs in: README.md's "Local dev auth" section (already fixed via this session) and potentially a shared Node.js troubleshooting reference if the codebase accumulates one.

## 2026-07-21 — [ci] An unset GitHub Actions `secrets.*` evaluates to empty string with no error, and masking makes the resulting misconfiguration undebuggable — use `vars.*` for non-sensitive config

Why: The original 2026-07-18 `build-images` failure was `${{ secrets.TELEGRAM_BOT_USERNAME }}` resolving to nothing because the secret had not been created yet; the workflow passed an empty `--build-arg` and the Dockerfile's `test -n` guard emitted a generic message that pointed at the Dockerfile rather than at the missing secret. GitHub documents both halves of this trap: an unset secret silently becomes an empty string, and secrets cannot be used in `if:` conditionals, so you cannot cheaply assert their presence. Compounding it, secrets are masked as `***` in logs by design — which means when the value is merely _wrong_ rather than missing, the logs cannot distinguish the two. GitHub's own criterion is sensitivity, not repo-hygiene: "if you need greater security for sensitive information such as passwords or API keys, you should use secrets instead of variables" (docs.github.com, Variables › Security Considerations). Configuration **variables** (`vars.*`, scopable to repository/organization/environment) are the correct vehicle for non-sensitive per-environment values — they render in plain text, so they are debuggable. Rule of thumb established here: masking is a cost paid for confidentiality; when the value is not confidential you pay the cost and receive nothing. Belongs in (guess): rules/ (a CI/secrets-handling rule) — likely `claude-ts-upstream` too, since it is stack-agnostic

Belongs in (guess): pairs with `rules/local/workflow.md` § Phase 4.5 (task-16 entry above) — possibly worth a QA-stage checklist item: "for any value driving a color/fill/visual state, view it rendered against real edge-case data, not just assert the returned number."

## 2026-07-29 — [pattern] Clamping a percent-driven progress bar to `Math.min(100, ...)` silently hides overspend magnitude — second occurrence of the same UI-visual-meaning gap

Why: `planner-category-row.ts`'s original `barWidthPercent = Math.min(100, Math.max(0, row().percent))` was numerically correct (never renders a >100%-wide bar) but made 100% spend and 300% spend render pixel-identical — the user couldn't see _how_ overspent a category was, only that it was overspent (same solid danger color either way). Fixed by splitting the bar into two proportional segments only when `percent > 100`: `withinBudgetPercent = 10000/percent` (green) + `overBudgetPercent = 100 - that` (red), summing to 100. This is the same class of bug as the entry directly above (unbudgeted-overspend 0% bar) — a value can satisfy its numeric contract (clamped width, no crash) while still failing to communicate the right thing visually. Two occurrences in the same component now; worth generalizing the QA checklist item from the entry above rather than treating this as a one-off. Belongs in (guess): `rules/local/architecture-angular.md` or a UI-review checklist — "any clamped/derived display value (width%, color tier) needs its unclamped source checked for >range cases that look identical once clamped."

## 2026-07-29 — [frontend] a single global `@layer base` cursor rule covers all 4 existing screens; native checkboxes/radios need it explicitly, `label:has()` targets the wrap-the-input convention already in use

Why: A desktop/mobile hover-cursor audit across records/history/planner found no per-component fixes were needed — one rule added to `apps/web/src/styles.css`'s `@layer base` (Tailwind v4, plain CSS per ADR-008) covers `button:not(:disabled)`, `[role='button']:not([aria-disabled='true'])`, `a[href]`, `select:not(:disabled)`, `input[type='checkbox']:not(:disabled)`, `input[type='radio']:not(:disabled)`, plus `label:has(input[type='checkbox']:not(:disabled))`/`label:has(input[type='radio']:not(:disabled))` for the label's own hover area, with `cursor: not-allowed` mirrored on each disabled counterpart. Two things worth keeping for future screens: (1) native checkboxes/radios get no pointer cursor by default in any browser — this must always be explicit, and (2) `label:has(input)` (not sibling `input + label`/`for`+`id`) was chosen because this codebase's existing markup (`category-manager.html`, `transaction-form.html`) already wraps the input inside the label rather than pairing them by id, so this selector shape is the one to keep reaching for. Placement in `@layer base` (not unlayered) matters — it lets Tailwind's own utility classes (`disabled:cursor-not-allowed`, an intentional `cursor-default` on a backdrop-dismiss button) still win the cascade. Belongs in (guess): `rules/local/code-style-angular.md` — add as the standard new-interactive-element checklist item so future components don't need per-component `cursor-pointer` classes.
