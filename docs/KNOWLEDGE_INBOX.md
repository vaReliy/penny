## 2026-08-08 — [process] The sandbox's Bash deny rule blocks `rm -rf` even for legitimate whole-directory deletion (e.g. removing a dissolved Nx lib) — use `find <dir> -type f -delete && find <dir> -depth -type d -delete` instead

Why: an implementation agent deleting the now-empty `libs/budget/validation` lib directory (after colocating all its exports elsewhere, per task) hit a sandbox denial on `rm -rf libs/budget/validation` — the deny rule fires regardless of whether the deletion is destructive-in-the-bad-sense or a legitimate, task-authorized cleanup of a lib with zero remaining consumers. The working substitute confirmed in that session: `find <dir> -type f -delete` (removes all files first) followed by `find <dir> -depth -type d -delete` (removes now-empty directories bottom-up, `-depth` ensures children are removed before parents). Generalises to any future whole-lib-deletion task in this sandbox. Belongs in (guess): `rules/local/shell-scripting.md` if one exists, or a note in `rules/cts/shell-scripting.md`'s sandbox-gotchas section — ambiguous because this may be specific to this project's sandbox config rather than a universal CTS constraint.

## 2026-08-08 — [testing] Vitest `coverage.thresholds` are a floor, not a target — a project can lose several points of real coverage with CI staying green the whole time, until it finally crosses the configured number

Why: `identity-core`'s vitest config recorded a calibrated baseline of 81.81%/78.94% (statements/functions) in its own comment, but thresholds were set at 76%/73% — a margin meant as slack, not a target. Coverage drifted down to 78.26%/75% (uncovered getters accumulating silently) with every CI run still green, because thresholds only fail the build on a _drop below the number_, never on a _drop from the baseline_. Nothing short of an explicit review caught it. Generalises: when a config comment records a "calibrated at X" baseline distinct from the enforced threshold, that gap is invisible drift budget that depletes silently — worth periodically diffing measured coverage against the recorded baseline, not just against the threshold. Separately: prefer wording a CI comment as an invariant ("test target is auto-inferred from vitest.config.mts presence") over a hardcoded count where possible — a stated mechanism can't drift the way a tally can. Belongs in: a testing-rigor rule — no `rules/local/` testing file exists yet in this repo; stack-agnostic, so `claude-ts-upstream` too.

## 2026-08-08 — [devops] `nginx.conf`'s `sub_filter` silently no-ops on zero matches — exact-string substitutions (e.g. CSP nonce injection into built `index.html`) need an explicit smoke check, not just a green build

## 2026-07-21 — [ci] An unset GitHub Actions `secrets.*` evaluates to empty string with no error, and masking makes the resulting misconfiguration undebuggable — use `vars.*` for non-sensitive config

Why: A `build-images` failure was `${{ secrets.TELEGRAM_BOT_USERNAME }}` resolving to nothing because the secret had not been created yet; the workflow passed an empty `--build-arg` and the Dockerfile's `test -n` guard emitted a generic message pointing at the Dockerfile rather than at the missing secret. GitHub documents both halves of this trap: an unset secret silently becomes an empty string, and secrets cannot be used in `if:` conditionals, so you cannot cheaply assert their presence. Compounding it, secrets are masked as `***` in logs by design — so when the value is merely _wrong_ rather than missing, the logs cannot distinguish the two. GitHub's own criterion is sensitivity, not repo-hygiene: "if you need greater security for sensitive information such as passwords or API keys, you should use secrets instead of variables" (docs.github.com, Variables › Security Considerations). Configuration **variables** (`vars.*`, scopable to repository/organization/environment) are the correct vehicle for non-sensitive per-environment values — they render in plain text, so they are debuggable. Rule of thumb: masking is a cost paid for confidentiality; when the value is not confidential you pay the cost and receive nothing. Belongs in: a CI/secrets-handling rule — no `rules/local/` CI file exists yet; stack-agnostic, so `claude-ts-upstream` too.

## 2026-08-07 — [testing] A test named for specific behavior but asserting only `toBeInstanceOf(Date)` (or similarly weak shape-only checks) passes identically against a correct implementation, a UTC-only one, or one off by a month — it is worse than no test at all

Why: `get-planner-summary.service.spec.ts` had a test literally named `'resolves the month filter to a Europe/Kyiv instant range passed to the repository'` whose body asserted only that `from`/`to` were `Date` instances. ## 2026-08-08 — [shell] Two `sed`-in-Dockerfile pitfalls that each silently produce a wrong-but-plausible result, caught only by independently recomputing the expected value

Why: a build-time CSP hash-injection step (computing a sha256 hash of an inline `<style>` block and writing it into an nginx config) shipped two sequential bugs, each passing its own build's `grep -q` verification step while producing the wrong hash. (1) The replacement `sed -i "s|$OLD_HASH|$NEW_HASH|g"` used a hardcoded literal of the _pre-fix_ hash as the search pattern — correct for exactly one commit, then a permanent silent no-op forever after, because GNU sed exits 0 on a zero-match substitution (not caught by `set -e`/errexit). Fix: never match a one-time historical literal; anchor the regex on structure instead (e.g. `s#(directive-name[^;]*)'sha256-[A-Za-z0-9+/=]+'#\1'sha256-$NEW_HASH'#`), or replace a stable placeholder token that never changes. (2) The tag-strip `sed 's/<\/?style>//g'` (no `-E`/`-r` flag) treated `?` as a literal character rather than a quantifier — pure POSIX BRE, not GNU's `\?` extension, and the pattern as written doesn't even invoke that extension correctly — so the tags were never stripped and the hash was computed over `<style>...content...</style>` including markup. Fix: use anchored non-quantifier patterns (`sed -e 's/^<style>//' -e 's/<\/style>$//'`) instead of relying on BRE/ERE quantifier behavior. Both bugs are invisible to a build-succeeded check and to a `grep -q "sha256-$HASH" file` self-verification, because that only confirms _a_ hash landed in the file, not that it's the _hash of the actual served content_ — only an independent, from-scratch recomputation (ideally via a second toolchain, e.g. cross-checking a shell pipeline against Node's `crypto.createHash`) catches this class of bug. Generalises beyond CSP: any build step that computes-then-injects a derived value and self-verifies only "did my write land" rather than "is the written value correct" has this blind spot. Belongs in (guess): `rules/cts/shell-scripting.md`'s sed-gotchas section (stack-agnostic, so also `claude-ts-upstream` material) — ambiguous only in whether it warrants its own subsection or a sentence appended to the existing sed-pitfalls list.

## 2026-07-21 — [ci] An `actions/cache` key must encode everything that determines the cached CONTENT, not just the lockfile — an exact key hit skips the save step, so a stale cache persists silently forever

Why: The Playwright browser cache was keyed `playwright-${{ hashFiles('pnpm-lock.yaml') }}`, but its content is determined by the installed browser SET, which the key did not encode. When the install step changed from chromium-only to all three engines, `pnpm-lock.yaml` was untouched, so the key still hit exactly — and `actions/cache` skips its post-job save on an exact hit. The steady state would have been: restore chromium-only cache → download firefox + webkit → save nothing → repeat forever, with tests passing the whole time and nothing in the logs announcing the waste. Confirmed empirically in both directions: the pre-fix run's final step read `skipped Post Cache Playwright browsers`, while the post-fix run (key prefix bumped `playwright-` → `playwright-all-`, `restore-keys` bumped to match so a stale entry cannot be partially restored) read `Cache not found for input keys: playwright-all-…` → downloads → `Cache saved with key: playwright-all-…`. Generalises to any cache whose content depends on a step's arguments rather than only on a manifest — the lockfile pins the tool VERSION, not which artefacts you asked it to fetch. Also recorded for calibration: the full three-engine e2e job ran 1m43s cold, so the "installing all browsers is too slow for CI" premise behind the original chromium-only install did not hold. Belongs in: a CI-caching rule — stack-agnostic, so `claude-ts-upstream` material too.

## 2026-07-21 — [ci] A GitHub Actions run marked "failure" can be mostly green — always read job-level conclusions before concluding the pipeline is broken

Why: One run showed as `failure` in the UI and in pasted logs, and was reasoned about (including by a dispatched `devops` agent working only from those logs) as "the pipeline is still failing." `gh run view <id> --json jobs` showed `ci` ✅, `build-images` ✅, `e2e` ❌ — two of three jobs were already green, and the only remaining defect (missing Playwright firefox/webkit binaries) was unrelated to the work everyone was chasing. ## 2026-07-23 — [config] Claude Code Bash allow rules are evaluated per-subcommand — a trailing `*` never authorizes chained commands, and compound patterns should be decomposed

Why: Per the permissions docs (§ Compound commands): "a rule like `Bash(safe-cmd *)` won't give it permission to run `safe-cmd && other-cmd`. The recognized command separators are `&&`, `||`, `;`, `|`, `|&`, `&`, and newlines. A rule must match each subcommand independently." Consequences applied here: (1) 26 accreted per-lib entries of the form `Bash(set -a && source .env && set +a && pnpm nx test <lib>)` were replaced by 4 composable rules — `Bash(set -a)`, `Bash(set +a)`, `Bash(source .env)`, `Bash(pnpm nx test *)` — covering every current and future lib with no settings churn while staying chain-safe; (2) wildcard allows like `Bash(grep *)`/`Bash(jq *)` are safe to commit at project level, while `cat`/`find`/`awk`/`sort` stay local-only (they can read `.env`, `-exec`, `system()`, or `-o`-overwrite — Read deny rules govern the Read tool, not Bash file reads); (3) `Bash(rm -rf *)` deny is prefix-fragile — an `rm -fr` variant was added, but deny rules are a speed bump, not a sandbox. Belongs in: a settings/permissions-authoring rule — `claude-ts-upstream` material, since it describes harness behaviour rather than anything project-specific.

## 2026-07-27 — [pattern] In-flight promise cache is a separate field from the TTL cache, not a replacement for it

Why: `GetExchangeRatesService.execute()` (`libs/budget/infrastructure/src/lib/get-exchange-rates.service.ts`) needed dedup for concurrent cache-miss calls hitting a rate-limited upstream (Monobank, ~1 req/5min). The fix adds a third field, `inFlightFetch: Promise<T> | undefined`, orthogonal to `cachedResponse`/`cachedAtMs` — cleared via `.finally()` on settle, independent of the TTL write/expiry cycle. Concurrent callers that miss the TTL check all await the _same_ promise object; each then independently runs its own post-await stale-serve/cold-throw logic, so existing single-caller semantics stay untouched with zero branching changes. This is the reusable shape for any other service wrapping a rate-limited external client behind a TTL cache: the dedup slot and the TTL cache are two independent fields, not one merged state machine. Belongs in: `rules/local/architecture-backend.md` (external-client + TTL-cache pattern) **if a second service needs this same treatment** — otherwise discard as a one-off. Deliberately kept pending that second occurrence rather than promoted on a sample size of one.

## 2026-08-07 — [docs] Prettier corrupts markdown when a bold span sits next to an inline-code glob starting with a double asterisk — write the glob in prose instead

Why: writing a bold span immediately followed by inline code containing a leading globstar (the ESLint/minimatch "match any directory" pattern) gives Prettier two readings of the asterisk run — bold-close versus glob-open. It resolves them wrongly and rewrites the line into genuinely broken output: emphasis markers left dangling, backticks glued to adjacent words with the surrounding spaces eaten, and stray backslash escapes inserted mid-pattern. It is silent, happens on `--write`, and the damage is a formatting change rather than an error, so `--check` passes afterward and CI never notices. Hit live this session in `rules/local/workflow.md` while documenting exactly such a glob. Notably this repo already has a commit whose message includes "fix markdown bold/glob corruption" (`e582626`), so this is at least the second occurrence and nothing yet prevents a third — the earlier fix repaired instances without recording the cause. Mitigations, in order of preference: (1) describe the pattern in prose ("a globstar-prefixed `application/**/*.ts` pattern") so no asterisk run ever touches an emphasis marker; (2) if the literal must appear, put it in a fenced code block rather than inline code; (3) never place inline code starting or ending with an asterisk directly adjacent to bold/italic markers. General rule: any inline code span whose content begins or ends with `*` or `_` needs a non-emphasis character between it and any adjacent emphasis marker. Belongs in: a new `rules/local/docs-style.md` (the consumer-owned mirror does not exist yet; `rules/cts/docs-style.md` is the natural topic home but is `Edit`-denied per this file's own header guidance) — and it is stack-agnostic, so it is also a `/cts-contribute` candidate for the upstream docs-style rule.

## 2026-08-07 — [tooling] A static `mise` install path on `PATH` silently ignores the repo's `mise.toml`, giving VS Code tasks the wrong Node
