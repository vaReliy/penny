## 2026-07-01 — cts-contribute: `.claude/settings.json` can reference hook scripts that were never added to `cts-payload.txt`

Why: `.claude/settings.json` (a payload file) referenced `.claude/hooks/knowledge-capture-nudge.sh` via a Stop hook command, but `.claude/hooks/` was never listed in `cts-payload.txt` — so a fresh `/cts-setup` or `/cts-update` in any consumer would sync a `settings.json` pointing at a script that doesn't exist locally. The gap only surfaced during a `/cts-contribute` session while diffing payload files against CTS; `cts-sync.sh` has no validation step that cross-checks `settings.json` hook commands against the payload manifest. ## 2026-07-07 — cts-sync.sh: self-overwrite of .claude/scripts/cts-sync.sh mid-run produces a spurious syntax-error exit code

Why: `cts-sync.sh` copies `.claude/scripts/` last in the payload order specifically so it overwrites itself only after everything else is synced (see comment above `sync_path()`). But bash does not fully buffer a script's source before executing straight-through code — when `copy_one` overwrites the running script file on disk, bash's subsequent reads for the remainder of the script land on bytes from the _new_ file at the _old_ file's byte offset, which don't align to any coherent statement. Observed result: the run completes all real work (payload copied/merged, `.cts-version` written, "Done. Review with: git diff" printed) but then bash throws a parse error and the process exits non-zero. Verified via `.cts-version` matching the new upstream SHA and `git diff --stat` matching the printed merge/conflict list — the non-zero exit does not mean the sync failed, contradicting the assumption in `.claude/skills/cts-update/SKILL.md` step 2 that non-zero exit means "did not run." Re-verified 2026-07-07 in an isolated sandbox after this exact sync pulled a new `cts-sync.sh` revision (commit `c512bd8`, which only reworked `merge_one`'s temp-file cleanup and left the self-copy ordering/comment untouched): reproduced the same class of failure with a synthetic mid-file upstream diff to `cts-sync.sh` (exit 127, `line: command not found` — a _different_ garbled error than the original run's `exit 2, syntax error near unexpected token '&&'`, confirming the error text/code is arbitrary noise from misaligned byte offsets, not a stable signal) — so the bug is still present in the version currently installed at `.claude/scripts/cts-sync.sh`. Root cause is structural (self-modifying script under `bash script.sh` invocation) and needs a fix in the sync engine itself, e.g. re-exec via `exec bash "$0" "$@"` right before the self-copy, or defer the self-copy to a `trap ... EXIT` that runs after the interpreter has already finished reading the file, or simply copy `.claude/scripts/cts-sync.sh` to a temp path and `cp` it into place as the very last statement with no code after it.
Belongs in (guess): claude-ts-upstream (cts-sync.sh script) — also `.claude/skills/cts-update/SKILL.md` step 2 wording should note this known false-negative on exit code

## 2026-07-13 — identity-infrastructure Mongo specs fail hard (not skip) without MONGO_TEST_URI, and are flaky under parallel vitest runs

Why: While wiring `vite:test`/`typecheck` into CI (task `2026-07-11-02`), a devops agent's first-pass CI comment claimed `libs/identity/infrastructure/src/lib/{mongo-connection,mongo-user-repository}.spec.ts` "skip if MONGO_TEST_URI is not set" — false. Both specs do `process.env['MONGO_TEST_URI'] ?? 'mongodb://localhost:27017'` with no `skipIf`/conditional guard, so without a reachable Mongo they fail hard (ECONNREFUSED, or `undefined.dropDatabase()` in `afterAll`). Separately, `mongo-user-repository.spec.ts`'s `updateProfile does not overwrite status (concurrent login + approval safety)` test was observed flaky against a _real_ local Mongo — 1 run failed (`expected 'Ada' to be 'NewName'`), the immediate next run passed all 24; Nx itself flagged it ("NX detected a flaky task"). Suspected root cause: Vitest runs spec files in parallel against the same `penny-test` database without per-file isolation/cleanup ordering guarantees. General lesson: never trust a comment/doc claim about test skip-behavior without grepping the actual spec for a skip guard; and Mongo-backed integration specs sharing one DB across parallel vitest workers need explicit isolation (unique DB/collection per run, or serialized execution) or they will intermittently fail in CI regardless of correct target wiring.
Belongs in (guess): rules/testing.md (Mongo-backed integration test isolation pattern) + a comment fix at the two spec files themselves

## 2026-07-13 — nx.json plugin-inferred target names diverge from plain `test`/`build`; CI must enumerate them explicitly

Why: `nx.json` registers `@nx/vitest` with `"testTargetName": "vite:test"` (not `test`) and `@nx/vite/plugin` with `"typecheckTargetName": "typecheck"`. Only `apps/api`/`apps/cli` define a plain `test` target in `project.json`; all 13 libs + `web` rely purely on the inferred `vite:test` target. `nx affected -t lint,test,build` silently skips any project lacking the requested target — no error, no "skipped" notice — so CI ran zero unit tests for 14 of 16 vitest-covered projects for an unknown period before this was caught (flagged in KNOWLEDGE_INBOX 2026-07-08, task created and closed 2026-07-13). General lesson: whenever `nx.json` plugin config renames an inferred target away from Nx's conventional default name, any CI/script invocation using the conventional name must be updated in lockstep, and it's worth a periodic `nx show projects --with-target <name>` sanity check against what CI actually invokes, since there's no automatic failure signal when a target is silently missing.
Belongs in (guess): rules/workflow.md (Nx Command Execution Policy section — note the vite:test/typecheck target names explicitly) or a cts-rule-auditor-style check for this repo

## 2026-07-13 — GitHub Actions `services.<name>.options` health-cmd needs single-token quoting, not docker-compose array syntax

Why: While adding a `mongo:7` service container to `.github/workflows/ci.yml` (task `2026-07-11-02`), the first-pass health-check used `--health-cmd mongosh --eval "db.adminCommand('ping')"` — syntactically valid YAML, but GH Actions passes `services.*.options` straight to `docker create`, which parses `--health-cmd` as taking exactly one token; the trailing `--eval "..."` became unrecognized positional args and `docker create` failed with `unknown flag: --eval`, exit 125 (verified locally by reproducing the exact `docker create` call). This means the service container would never be created and the CI job would fail before any step ran — a silent trap because the YAML itself has no lint error. Fix: wrap the whole command as one quoted token, e.g. `--health-cmd "mongosh --eval \"db.adminCommand('ping')\""`. The `docker-compose.yml` array healthcheck form (`test: ['CMD', 'mongosh', '--eval', "..."]`) does not translate directly to GH Actions service `options` syntax. Always dry-run `docker create --health-cmd ... <image>` locally before trusting `services.*.options` health-cmd quoting in CI.
Belongs in (guess): rules/docker-commands.md or rules devops skill (GH Actions service-container health-cmd quoting gotcha)

## 2026-07-13 — GitHub Actions workflow branch trigger gotcha: workflows silently never execute if current branch is not in `on.branches` filter

Why: During task `2026-07-11-02`, CI tests were added for the `vite:test` and `typecheck` targets against the `skeleton` branch, but the `.github/workflows/ci.yml` file inherited an earlier `on.branches: [master, develop]` filter (or similar). This meant the CI job never ran on `skeleton` — no error, no warning, no log message. The job simply did not exist in the GitHub Actions UI for that branch. Debugging required trial-and-error: "why isn't CI running?" → "is the YAML valid?" → "are there syntax errors?" → "does it run on master?" → finally realizing the branch filter silently rejected the entire workflow. Fix: always verify that the current branch is listed in the `on.branches` allow-list when adding a new workflow or modifying branch-specific logic. A common gotcha on multi-branch repos with environment-specific workflows.
Belongs in (guess): rules/git-operations.md or a devops skill guide (GitHub Actions branch-filter silent-skip gotcha)
