## 2026-07-07 — cts-sync.sh: self-overwrite of .claude/scripts/cts-sync.sh mid-run produces a spurious syntax-error exit code

Why: `cts-sync.sh` copies `.claude/scripts/` last in the payload order specifically so it overwrites itself only after everything else is synced (see comment above `sync_path()`). But bash does not fully buffer a script's source before executing straight-through code — when `copy_one` overwrites the running script file on disk, bash's subsequent reads for the remainder of the script land on bytes from the _new_ file at the _old_ file's byte offset, which don't align to any coherent statement. Observed result: the run completes all real work (payload copied/merged, `.cts-version` written, "Done. Review with: git diff" printed) but then bash throws a parse error and the process exits non-zero. Verified via `.cts-version` matching the new upstream SHA and `git diff --stat` matching the printed merge/conflict list — the non-zero exit does not mean the sync failed, contradicting the assumption in `.claude/skills/cts-update/SKILL.md` step 2 that non-zero exit means "did not run." Re-verified 2026-07-07 in an isolated sandbox after this exact sync pulled a new `cts-sync.sh` revision (commit `c512bd8`, which only reworked `merge_one`'s temp-file cleanup and left the self-copy ordering/comment untouched): reproduced the same class of failure with a synthetic mid-file upstream diff to `cts-sync.sh` (exit 127, `line: command not found` — a _different_ garbled error than the original run's `exit 2, syntax error near unexpected token '&&'`, confirming the error text/code is arbitrary noise from misaligned byte offsets, not a stable signal) — so the bug is still present in the version currently installed at `.claude/scripts/cts-sync.sh`. Root cause is structural (self-modifying script under `bash script.sh` invocation) and needs a fix in the sync engine itself, e.g. re-exec via `exec bash "$0" "$@"` right before the self-copy, or defer the self-copy to a `trap ... EXIT` that runs after the interpreter has already finished reading the file, or simply copy `.claude/scripts/cts-sync.sh` to a temp path and `cp` it into place as the very last statement with no code after it. Belongs in: .claude/scripts/cts-sync.sh (code fix — approach not yet decided, see three candidates above) — also `.claude/skills/cts-update/SKILL.md` step 2 wording should note this known false-negative on exit code

## 2026-07-19 — derived-balance `$sum` forces numeric BSON Money storage (not the transport string)

Why: The shared `Money` VO (`libs/shared/util/src/lib/money.ts`) holds `bigint` minor units but `toJSON()` serializes `amount` as a _string_ (`SerializedMoney`, precision-safe for transport). The budget domain's chosen derived-balance strategy aggregates account balance via a Mongo `$sum` over stored transaction amounts — and `$sum` cannot sum strings. Therefore infrastructure must store money as a _numeric_ BSON type (64-bit Long minor units, not int32 which overflows past ~21M UAH, not the transport string), with the mapper round-tripping `bigint ↔ Long` and never touching float. This couples the balance strategy and the money-storage representation. Belongs in (guess): captured permanently by `DECISIONS.md` ADR-007 — delete once the transaction repo/aggregation work records the Long-minor-units storage contract in code.

## 2026-07-19 — adding a new Nx `scope:*` domain requires an explicit eslint depConstraint or the fuse is open

Why: `eslint.config.mjs`'s `@nx/enforce-module-boundaries` depConstraints currently enumerate only `scope:shared` and `scope:identity`. A source tag with no matching `onlyDependOnLibsWithTags` rule is NOT fenced by default — it can import anything. So standing up `libs/budget/*` has a hard prerequisite: add `{ sourceTag: 'scope:budget', onlyDependOnLibsWithTags: ['scope:budget','scope:shared'] }` to the config BEFORE the first budget lib lands, else the onion/scope fuse silently doesn't apply to budget. This is an executable-config edit (never trivial-tier). Separately confirmed: `type:validation` libs may depend ONLY on `type:util` (not `type:contracts`) — LIVR schemas are self-contained runtime rule objects and must not import DTO/contract TS types; a budget `type:validation` lib therefore cannot import from a budget `contracts` lib. Belongs in (guess): `rules/architecture.md` (Nx tag section) — the "new domain ⇒ new depConstraint" prerequisite is a general rule, not budget-specific; the `type:validation`→`type:util`-only constraint likely already lives in the eslint config but is worth stating in the rules doc.

## 2026-07-20 — Angular/Playwright test-writing gotchas found during web-shell restyle

Why: Four independent, non-obvious gotchas surfaced while writing/auditing tests for the new `libs/shared/web-shell` shell component and its e2e coverage:

1. `[routerLink]` does not persist as a DOM attribute at runtime — `querySelectorAll('a[routerLink]')` always returns 0 matches; use a structural/positional selector (`nav > a`, or a container-scoped plain `a`) instead when asserting on router-link elements in component specs.
2. `RouterTestingHarness.navigateByUrl(url, ComponentType)` returns the _component instance_, not a `ComponentFixture` — `whenStable()`/`detectChanges()` live on `harness.fixture`, not on the returned value; easy to typo into `TypeError: fixture.whenStable is not a function`.
3. Playwright's `devices['...']` presets set `defaultBrowserType` and cannot be applied via `test.use()` inside a `describe` block ("forces a new worker" error) — only at top-level test-file scope or in the config's `projects` array. For a mobile-viewport-only smoke test layered onto existing chromium/firefox/webkit projects, use `test.use({ viewport: {...}, hasTouch: true })` instead of a device preset.
4. An e2e logout-flow test that mocks `/auth/me` unconditionally will deadlock: `loginGuard` on `/login` re-checks `/auth/me` and bounces an apparently-still-active user straight back, so `page.waitForURL('**/login')` times out. The mock must flip to 401 once the logout endpoint is actually hit, simulating real session invalidation. Belongs in (guess): `vitest-testing`/`playwright-expert` skill notes, or a shared "Angular+Playwright gotchas" reference — none of these are project-specific, they'd help any Angular 17+/Nx/Playwright repo.

## 2026-07-20 — Node's `--env-file` flag does not expand shell-style variable references in .env values

Why: The CLI commands in README.md's "Local dev auth" section failed with `Error: Missing env var: MONGO_URI` even when `.env` was present, because users ran `node --env-file=.env ... ` directly. Node 22's native `--env-file` flag does not perform shell-style variable expansion (e.g., `${MONGO_USER}`) — it reads and sets the literal unexpanded string as the env var value. Since `.env.example` documents `MONGO_URI=mongodb://${MONGO_USER}:${MONGO_PASSWORD}@...` (using bash-style interpolation), the value must be expanded by bash before Node receives it. The fix: source `.env` through bash first with `set -a && source .env && set +a &&` prefixed to the command, which expands all `${...}` references and exports them before Node runs. This is a gotcha any Node.js dev hitting `--env-file` with a `.env` that contains variable references will encounter. Belongs in: README.md's "Local dev auth" section (already fixed via this session) and potentially a shared Node.js troubleshooting reference if the codebase accumulates one.

## 2026-07-20 — any lib that imports anything from `shared-util` (even `import type`, even transitively through a barrel) needs `"target": "es2020"` in its own `tsconfig.json`, not just `shared-util`'s

Why: Standing up `libs/budget/core` (task `2026-07-16-05-budget-core-entities`), `budget-core:typecheck` failed with `TS2737: BigInt literals are not available when targeting lower than ES2020` pointing at `libs/shared/util/src/lib/money.ts` (the `0n` literals in `Money.zero`/`isZero`/`isNegative`) — a file this lib never edited. Root cause: `tsconfig.base.json` sets `target: es2015` workspace-wide; `shared-util`'s own `tsconfig.json` overrides `target: es2020` locally so its own typecheck passes, but that override is NOT inherited transitively by a consumer. Since Nx libs are consumed from source via `tsconfig.base.json` path aliases (not published/prebuilt), any consumer whose `tsconfig.spec.json`/`tsconfig.json` program ends up including `money.ts` recompiles it under its own (lower) `target`, and the BigInt literals fail. Originally believed scoped to _value_ imports of `Money` (constructing `Money.fromMinorUnits(...)`, not just typing a field `amount: Money`) — `identity-core` never hit this because it never imports `Money` by value. **Broadened 2026-07-20 during `2026-07-16-06-budget-contracts-livr-validation`**: `libs/budget/contracts` hit the identical failure via `import type { SerializedMoney }`/`{ CurrencyCode }` from `shared-util` — a type-only import through `shared-util`'s `index.ts` barrel. tsc must still fully resolve the module graph behind a barrel import even for `import type`, so it pulls in `money.ts` regardless of whether the importing file constructs a `Money` value. The type-only exemption does not actually hold once a barrel is involved. Fix applied both times: add `"target": "es2020"` to the consuming lib's own `tsconfig.json`, mirroring `shared-util`'s override (done for `libs/budget/core` and `libs/budget/contracts`). Belongs in: `rules/nx-generators.md` or `rules/architecture-backend.md` — any new lib that imports anything (value or type) from `shared-util`, directly or via a barrel, should proactively add this override rather than discover it at typecheck time.

## 2026-07-20 — LIVR v2.10.2 is unknown-key-safe and object/array-injection-safe by construction, not convention

Why: Security audit of the budget vertical's LIVR schemas (`libs/budget/validation`, task `2026-07-16-06-budget-contracts-livr-validation`) traced two properties directly in LIVR source (`node_modules/.pnpm/livr@2.10.2/lib/rules/**`, `Validator.js`) rather than assuming them from test coverage: (1) every built-in rule (`string`, `like`, `one_of`, `positive_integer`, `max_number`, `iso_date`, ...) gates on `util.isPrimitiveValue(value)` first, which checks `typeof value === 'string'|'number'|'boolean'` — any object or array (e.g. a Mongo-operator-injection payload like `{ $gt: '' }`) fails this gate and returns `FORMAT_ERROR` before the rule's own logic runs; (2) `Validator.validate()` builds its output by iterating the _schema's own_ declared field names (`for (const fieldName in this.validators)`), never copying arbitrary keys from the input `data` object — so fields absent from the schema are silently dropped, not passed through, with no opt-in "strict mode" needed. Both properties hold for any LIVR schema in this repo without per-field enforcement. Not yet checked: array-typed filter fields (none exist yet in the budget vertical) — an array of operator-objects would need its own array-of-scalar rule verification once such a field is added. Belongs in: `rules/validation-authorization.md` — save future security audits from re-deriving this from `node_modules` source each time.
